Warehouse replenishment

Debugging · 1 of 4

peek: quick, but it edits your code

  • Put it between two stages, read what flows past. Move it one stage further and compare.
  • Elements arrive one at a time, interleaved with later stages, not stage by stage (laziness).

For debugging only.

You have to change the code (and remove it again). A peek whose action changes state is a bug waiting to happen. The JDK documents it as existing mainly to support debugging.

peek is intermediate: a pipeline of only intermediate operations prints nothing.

Debugging · 3 of 4 · IntelliJ

Trace Current Stream Chain

  1. Breakpoint on the line where the stream starts in actionsCanBeChained (Database.orders.stream()). Run in Debug.
  2. In the toolbar of the Debug window open More → Trace Current Stream Chain.
  3. The Stream Trace dialog has a tab per stage: what it received and what it returned. Flat Mode shows everything in one overview.

Good to know

  • Comes with the Java Stream Debugger plugin (installed and enabled?)
  • The stream must end with a terminal operation. Result-less ones such as forEach are not drawn in Flat Mode.
  • Only works on your own project code, not library code.
You see at which stage an element disappeared (filter, distinct) or changed (map).
Debugging · 4 of 4

Reading a stack trace through java.util.stream

  • Many frames from java.util.stream (ReferencePipeline, Sink, AbstractPipeline) sit between your lambda and the terminal operation: that is plumbing, ignore it.
  • Read from the top for the exception type and message, then find the first frame in your code: the lambda that failed (Main.lambda$…).
  • The last frame of your code lower down is the line with the terminal operation that started the pipeline.
  • The trace does not say which element failed: use a lambda breakpoint (with a condition) or peek.
  • Because of laziness the failure happens at the terminal operation, not where you wrote the faulty map.
peek for a quick look · lambda breakpoint for one element · Trace Current Stream Chain for the whole chain.

Boolean questions and reduce

OperationExample on the course dataResult
anyMatch(p)orders.stream().anyMatch(o -> !o.paid())true
allMatch(p)orders.stream().allMatch(Order::paid)false
noneMatch(p)orderLines.stream().noneMatch(l -> l.quantity() > 2)true

reduce(acc)orderLines.stream().map(OrderLine::total).reduce(Double::max)Optional[6.0]
  • anyMatch stops at the first hit; allMatch and noneMatch stop at the first miss. On an empty stream: false, true, true ("all of nothing" is vacuously true).
  • findAny() is findFirst() without the promise: prefer findFirst().
  • reduce is the general form of sum, max and count, but mapToDouble(…).sum() is usually better: shorter, and no boxing.
Terminal operations · beyond what we run

Handling an Optional

min, max, findFirst, findAny, average, reduce(acc): the stream may be empty, so you must decide what "nothing" means.

CallWhen empty
orElse(-1)-1 (the argument is always evaluated)
orElseGet(() -> -1)-1 (the supplier only runs when empty: use it when the fallback is expensive)
orElseThrow(() -> new IllegalStateException(…))throws that exception
orElseThrow()throws NoSuchElementException: No value present
ifPresent(consumer)does nothing
map(f)stays empty

orElse(null) is a smell: it turns the explicit "maybe" back into a null the next reader may forget to check. Choose on purpose: a meaningful default, orElseThrow when absence is a bug, or keep working inside the Optional.

Main.java ends max, min and findFirst with .orElse(null) and .orElse(-1). On the course data that fallback never fires (18 lines, so max and min always find one; findFirst finds the unpaid order 3). The fallbacks only keep the demo short.

orderLines.stream().max(Comparator.comparingDouble(OrderLine::total))
    .map(OrderLine::articleId).map(Database::getArticle).map(Article::name);   // Optional[Taco]

Gatherers: custom intermediate operations

A collector can only end a pipeline; a gatherer is an intermediate operation, so the stream goes on. Final since Java 24: on JDK 25 no --enable-preview. Ideal for operations that look at more than one element: windows, running totals.

GathererExampleResult
windowFixed(n)names.stream().gather(Gatherers.windowFixed(3)).toList()[[Apple, Beer, Candy], [Chicken, Coffee, Donuts], [Ice Cream, Pineapple, Pizza], [Taco]]
windowSliding(n)names.stream().limit(4).gather(Gatherers.windowSliding(2)).toList()[[Apple, Beer], [Beer, Candy], [Candy, Chicken]]

Terminal operations

Key takeaways

  • A terminal operation starts the pipeline; without one nothing runs.
  • Prefer .toList() unless you need a mutable list or want null rejected.
  • Never rely on the order of a Set (or Map) when printing or comparing: sort first.
  • findFirst() and other short-circuiting operations can stop the pipeline early.
  • groupingBy → Map<key, List>; partitioningBy always has exactly two keys; toMap fails on duplicate keys without a merge function.
  • reduce is the general fold, but sum() is usually better.
  • An Optional says "maybe nothing": pick a default, throw, or keep mapping. orElse(null) hides the problem again.
  • Gatherers (final in Java 24): windows, running totals and folds that collectors cannot express.

Pitfall · broken on purpose · run Main

Endless streams

Part 1
Part 2: looks safe because of limit(10)

1. A never-ending 0 1 0 1 0 1 …. After 10 s the lesson stops waiting, but the pipeline keeps running in the background.

2. Prints 0 1 and then hangs, while the first pipeline is still flooding the console.

The output is huge and the program does not stop by itself: press the red Stop button in IntelliJ.

Pitfall · Endless streams

Why it goes wrong, and how to fix it

Why

  • iterate(seed, next) has no end. Only a short-circuiting operation (limit, findFirst, takeWhile, anyMatch…) can end it.
  • The timeout only stops waiting: forEach never checks for interruption and the executor is never shut down.
  • distinct() before limit(10): the stream only ever holds two distinct values, so after two elements nothing passes and limit waits for ten that never arrive.

Fix

takeWhile(i -> i < 10) would not help here: on 0 1 0 1 … the condition is always true.

Infinite streams need a short-circuiting operation, and the order decides whether it can do its job.
Pitfall · run Main

limit and skip: guess first

How many numbers does it print? Guess, then run it.

limit(10).skip(5): take the first 10 (0..9), then drop the first 5 → 5 numbers
skip(5).limit(10): drop the first 5, then take 10 (5..14) → 10 numbers
Each step only sees what the previous step passes on. Changing the order of filter, map, distinct, limit and skip can change the result, not only the speed.
Pitfall · slow on purpose · run Main (~40 s)

Calling a service inside a loop or stream

N+1: one slow call per line
Bulk first, then work in memory

Database.getArticle(id) pretends to be a remote call (100 ms). 18 order lines = 18 calls per run. The bulk variant makes one call (300 ms) and uses a Map.

That is the N+1 problem: one call to get the lines, plus N calls to get the details.

A for loop and a stream are equally slow here. The stream only makes it harder to notice, because the call hides inside a lambda.

Pitfall · N+1

Four timings, one ratio

Each variant runs the same work 10 times. Measured on JDK 25, Apple silicon. The absolute numbers vary per machine, the ratio does not.

fetchArticleInForLoop ~18 700 ms
fetchArticleInStream ~18 700 ms
fetchArticleFirst (loop) ~3 050 ms
fetchArticleFirst (stream) ~3 050 ms
Never call a database, REST service or any slow method per element inside map, filter or a loop body if you can fetch in bulk first. About 6x faster.
